# 全文

## Slide 1 — コスプレ文化が生む「制作能力」を測る（111字 / 20秒）

> コスプレ文化が毎週生み出している制作能力を、私たちは社会資源として一度でも測ったことがあるでしょうか。衣装の話ではありません。毎回違う仕様を、一点だけ、締切までに、あり合わせの材料で作る。私が測ったのは、この生産能力です。

## Slide 2 — なぜコスプレなのか ── 毎回違うものを作る生産体制（118字 / 22秒）

> 製造業は固定仕様を大量に、計画通りに作ります。コスプレ制作は逆です。毎回違う仕様、一点物、締切駆動、現場での作り直し、そして作り方を公開する規範。危機のとき本当に足りなくなるのは、誰も備蓄していない規格外の少量品です。ここが一致します。

## Slide 3 — その能力は、供給ショックで転化するか？（117字 / 22秒）

> 四十体のエージェントが百五十六週かけて、技能と制作物と関係を蓄積します。そこへ供給ショックを起こす。渡すのは属性で書かれた未知の仕様だけで、何を作るべきかは一度も指示していません。意図はLLMが決め、実現できるかはコードが判定します。

## Slide 4 — Agent は既存 Project を未知仕様へ適応させた（80字 / 15秒）

> これは実際のログです。手持ちの制作物は要求を満たしていません。エージェントは属性を二回作り替え、要求に到達させて供給しました。制作試行ごとに記録された経路です。

- 画面右の動画領域に M1 の実行映像（**10倍速**。実行全体 38.5秒 → 約 3.85秒）
- テロップ: `M1 / API-free simulation` / `156 accumulation steps` / `10× playback`

## Slide 5 — しかし Transition は 0/20 だった（99字 / 18秒）

> 事前登録した転化の基準は四つ。供給者の形成、供給の継続、協調関係の形成。この三つは二十ラン全てで満たされました。届かなかったのは量の条件だけです。四条件が同時に成立したランは、二十のうちゼロでした。

## Slide 6 — なぜか ── 仕様適応後の production success が律速した（77字 / 14秒）

> では何が量を止めていたのか。制作試行を分解すると、材料でも設備でも時間でも止まっていません。止めていたのは、仕様に合わせて作り替えた後の制作成功率でした。

**※ P\*、8.2倍、7.4倍、感度分析の詳細は読み上げない。** Backup B2 で答える。

## Slide 7 — そして私は「6/20」を採用しなかった（112字 / 21秒）

> 実行後に、設定ファイルが事前登録の閾値と食い違っていたと分かりました。実行時の設定なら転化は二十中六です。私は事前登録の値を適用し、ゼロを主結果にしました。ログは一行も書き換えず、主結果の再判定はAPIを使わず再現できます。

**※ タイトルと副題（── 実行時 config が事前登録値と違っていたから）は同時に表示する。**
タイトルだけ先に出すアニメーションにしない。

## Slide 8 — 次は現実のコスプレ制作能力を測る（99字 / 18秒）

> 本研究が出したのは供給量の予測ではなく、現実で何を測るべきかの特定です。実際の制作者が未知の仕様にどこまで適応できるのか。次はそれを測ります。好きなことを続けてください。それが安全保障になる社会へ。

# M1 録画手順

```bash
python -m experiments.m1_smoke --seeds 5 --summary outputs/demo_m1_recording.csv
```

## 条件（すべて確認済み）

| 条件 | 状態 |

## 録画と編集

1. **通常速度で録画する。** 実測で総 38.5秒、進捗行は **1行あたり約 7.4秒**
2. **実行全体（約 38.5秒）を素材とする**（区間の切り出しをしない）
3. 全体を **10倍速**にして **約 3.85秒**へ収め、**4秒枠**へ挿入する
4. **実行出力そのものは改変しない。** 変更するのは**表示上の再生速度だけ**であり、
   M1 の実行条件・コード・ログ・結果は一切変更しない
