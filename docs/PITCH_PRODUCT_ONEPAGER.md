# COSPLAY RESERVE — Product One-Pager

> **コスプレ文化が毎週生み出している制作能力を、私たちは社会資源として一度でも測ったことがあるだろうか。**

---

## 何を売るか

**「仕様の穴」を埋められる制作能力が、地域にどれだけ潜在しているかを測り、危機時に接続する仕組み。**

3層構成。

| | 製品 | 内容 |
|---|---|---|
| ① | **COSPLAY RESERVE Scan** | 制作能力（技能・設備・材料・制作履歴）の登録と可視化 |
| ② | **COSPLAY RESERVE Simulator** | 供給ショックのシミュレーションと診断 ← **今回の PoC はここ** |
| ③ | **COSPLAY RESERVE Response** | 危機時に、希望した個人・資材企業・自治体を接続 |

今回到達したのは**主として ② の PoC** である。① は登録スキーマの設計まで、③ は未着手。

---

## なぜコスプレなのか

「技能を持っているから」ではない。**コスプレ制作の生産体制そのものが、供給危機の需要形態と一致している**からである。

| | 製造業 | コスプレ制作 |
|---|---|---|
| 仕様 | 固定仕様 | **毎回ちがう仕様** |
| ロット | 大量 | **一点物** |
| 納期 | 計画納期 | **締切駆動** |
| 現場修復 | 想定外 | **日常** |
| 知識 | 秘匿 | **作り方の公開共有が規範** |

危機時に本当に不足するのは、**誰も備蓄していなかった規格外の少量品**である。標準品は備蓄が埋める。埋まらないのは**仕様の穴**だ。

> 「新しい仕様のものを、少量、短納期で、あり合わせの材料で作る」——
> これはコスプレ制作の**平常運転**であり、危機時に**最も希少な能力**である。

平時に訓練されているのは技能だけではない。**仕様が毎回変わる前提の段取り、現場で直す判断、作り方を公開する規範**まで含めた生産体制ごとである。ここが模倣困難性の源泉であり、本製品の moat はコスプレ文化以外では成立しない。

## 今回何を確認したか — **これは「役割の測定」である**

事前登録した転化基準（4条件の同時充足）に対し、20 run の結果：

> **以下は主結果である。** 判定は事前登録値（`share>=0.25` / `suppliers>=3` / `duration>=4` / `edges>=2`）による corrected adjudication であり、**人間判断として確定済み**。実行時 config の暫定値（0.20 / 3 / 3 / 2）による転化 6/20 は、事前登録との同期不一致を示す**副次的記録**として保持しているだけで、本ピッチの根拠には使用しない。

| 問い | 判定基準 | 結果 |
|---|---|---|
| 仕様を満たす供給者が形成されたか | `active_supplier_count >= 3` | ✅ **20 / 20 run** |
| 供給が継続したか | `supply_duration >= 4 step (24h)` | ✅ **20 / 20 run** |
| 協調関係が形成されたか | `coordination_edges >= 2` | ✅ **20 / 20 run** |
| **量が閾値に達したか** | `community_supply_share >= 0.25` | ❌ **転化 0 / 20 run** |

読み方は明確である。

> **未知の仕様には届いた。量には届かなかった。**

これは失敗ではない。**一点物メイカーの能力プロファイルの測定**である。

> **コスプレ制作能力は「量」の補完ではなく「仕様の穴」の補完である。**

Agent には答えを一切与えていない（「◯◯を作れ」という指示は存在しない）。にもかかわらず Agent は**既存の制作対象を要求仕様まで modify して供給に到達した**。その経路は集計値からの推論ではなく、**provenance に直接記録された事実**である：

```
before  attr_0=0.45, attr_2=0.40   （要求を満たさない既存作品）
modify  attr_0 +0.15, attr_2 +0.15 （Agent 自身の判断）
after   attr_0=0.60, attr_2=0.55   → 要求仕様 (>=0.60, >=0.55) を充足 → 供給成立
```

供給を伴う制作記録 606 件のうち **282 件が、同時刻に協調関係を持つ作り手によるもの**（20/20 run で発生）。**仕様適応能力は観測され、量産能力は観測されなかった。**

### 研究上の判定と、製品仮説の根拠を混同しない

この2つは**水準が違う**。同じ表から読み取れるが、同じ主張ではない。

| | 内容 | 位置づけ |
|---|---|---|
| **研究上の判定** | **Transition = 0 / 20 run**（4条件の同時充足）。これが唯一の転化判定であり、主結果である | 事前登録済み・確定 |
| **製品仮説の根拠** | 仕様適応（provenance に直接記録）／供給者形成 20/20／継続 20/20／協調 20/20 | **モデル内で観測された事象**。製品仮説はここから導く |

**製品仮説を「研究上の転化が成立した」と言い換えてはならない。転化は成立していない。**
そして、**モデル内で観測されたことは、現実のコスプレイヤーで実証されたことを意味しない。** 本 PoC はモデル内実験であり、実データによる検証は Pilot の課題である。

### 必ず併記する制約

- **本モデルは実データでキャリブレーションされていない。仮説生成ツールである。**
- `community_supply_share` は**累積比**であり、比較基準は毎 step 一定量で積み上がる。そのため share の最大値は観測窓の**初期に出て以後低下する**（across-run max: t+0 で 0.250 → t+7 で 0.204）。一方 `supply_duration >= 4` は**構造上 t+3 以降でしか成立しない**。**share が最も高い時間帯と、duration が資格を得る時間帯が重ならない。**（share 条件を1 step でも満たしたのは 2/20 run、いずれも t+0 で duration=1 のとき。）
- したがって正しい記述は「量が足りない」ではなく、**「本モデルの操作的定義のもとでは量が律速だった」**である。

## 誰が買うか / 誰がチャネルか

単独の買い手は存在しない。**予算主体とチャネルを組ませる設計**が本製品の要である。

| 関与者 | 持つもの | 持たないもの | 役割 |
|---|---|---|---|
| **自治体**（防災・危機管理・文化振興・地域産業） | 予算、危機時の需要 | コミュニティへの接点 | **予算主体（buyer）** |
| **コスプレイベント運営会社** | 参加者との接点、登録の導線 | 予算、危機時の需要 | **チャネル** |
| **コスプレ関連企業**（造形材料・3Dプリンタ・ミシン・衣装） | 資材の供給網 | ボトルネックの所在 | **第三の関与者**：どの材料が律速かを本製品で調べ、**平時に資材配置を設計する主体** |

**データ取得の課題はイベント運営会社の登録導線で解く。** 参加登録フローに **Capability 登録を1画面追加する**。新規の収集チャネルを作らない。

**個人のコスプレイヤーは buyer ではない。** 本人が希望した場合にのみ Capability を登録し、案件提示に対して**任意で**参加する。**報酬を伴ってよい。**

> **「文化を徴用する」のではない。「文化の中で育った能力に、新しい活躍先を作る」。**
> 「安全保障に参加してください」ではなく、**「好きなことを続けてください。それが安全保障になる社会」**（SPEC §31）。

## 最初の Pilot の設計

**自治体1 × イベント運営会社1 × 資材企業1** の三者で1地域。

1. **登録**：運営会社が主催する1イベントの参加登録に Capability 登録画面を1枚追加（任意・本人希望のみ）。目標は網羅ではなく、**技能／設備／材料の分布が取れること**。
2. **診断**：自治体が実際の想定需要を**仕様として**入力する（例：「フェイスシールド相当品 50 枚を 72 時間以内」）。Simulator が **転化到達可否・到達までの時間・律速条件**を返す。
3. **資材ボトルネック**：どの材料・設備が律速かを資材企業へ報告し、**平時の資材配置設計**に反映する。
4. **Response は接続の合意形成まで**。実発動は Pilot の範囲外。

成果物は「動員できる人数」ではなく、**「この地域はどの仕様の穴を、どれだけの時間で埋められるか」の診断書**である。

## 転化基準を顧客が設定できること（機能）

**「何をもって意味のある供給とみなすか」は文脈依存である。** 病院がフェイスシールドを 50 枚必要とする場合と、マスクを 5000 枚必要とする場合では、基準が異なる。

本製品は、**転化判定の4閾値（量・供給者数・継続時間・協調関係）を顧客が設定できる。**

これは研究上の限界の言い換えではなく、**実運用に必要な機能**である。50 枚の案件に 5000 枚の基準を当てれば、埋められる穴を「埋められない」と誤診する。

> **なお研究側の閾値は事前登録値のまま変更しない。** 製品の可変閾値と、研究の固定閾値は別物として扱う。

## 課金単位（金額より先に、何に対して課金するか）

| 層 | 課金対象 | 単位 |
|---|---|---|
| ① Scan | **診断対象コミュニティ1件**（登録者数に比例させない — 登録を増やす動機を歪めない） | 年額 |
| ② Simulator | **診断シナリオ1本** = 〈仕様 × 数量 × 納期 × 転化基準〉の1組 | 従量 |
| ③ Response | 平時の**待機**（reserve retainer）＋ 接続が**成立した**とき | 年額 + 成果 |
| 資材企業 | **ボトルネック診断レポート**（材料・設備の律速分析） | 年額 |

登録者数課金にしない理由：**登録を増やすことが目的化すると、本人の希望に基づく任意登録という原則が壊れる。**

## まだ証明できていないこと

- **現実のコスプレイヤーが危機時に供給できることは証明していない。** 本 PoC はモデル内実験であり、実データでキャリブレーションされていない。**モデル内で仕様適応・供給者形成・継続・協調が観測されたことは、現実の実証ではない。**
- **現実の供給量は予測できない。** 本モデルの数値は現実のスケールを持たない。
- 転化 0/20 は、**モデルの操作的定義のもとで量が律速だった**という測定結果であって、コスプレ制作能力の実力の上限ではない。
- **① Scan の登録スキーマが現実の制作能力を捉えられるかは未検証。** Pilot の第一目的はここである。
- **③ Response は未着手。** 危機時の実発動、法的責任、品質保証、対価の設計はいずれも未解決。
- 2×2 因子（ネットワーク構造 × 相互学習）の主効果は、seed 間ばらつきに埋もれており**結論を出せる規模ではない**（n=5/セル）。
- 本 PoC は「協調関係 >= 2 が構造的に測定可能なネットワーク」という**条件付き標本**である（9 seed 中 4 seed が対象外）。

## 拡張可能性

同じ生産体制の特徴（毎回ちがう仕様／一点物／締切駆動／現場修復／作り方の公開共有）を持つ他の制作文化へ、同一の測定枠組みを適用できる可能性がある。
