## 0. この文書の読み方 — 2種類の提案の分離

SPEC.md §32 は「研究命題を変更する提案と、実装方法を改善する提案を明確に分離せよ」と要求している。本文書では全提案に以下のタグを付与し、末尾（§13）に一覧表で再掲する。

| タグ | 意味 | 扱い |
|---|---|---|
| **【実装提案】** | 研究目的を変えずに実装方法を改善するもの | 承認不要。レビュー後に着手可。 |
| **【要承認】** | 研究命題そのものに触れるもの | SPEC §32 の指定形式（**問題 / なぜ問題なのか / 変更案 / 変更しなかった場合の影響**）で記述。**人間の承認を待つ。** |

【要承認】は本レビューで3件ある（§12 に4点セットで詳述）。要旨のみ先に挙げる。

1. **時間スケール**（§25）: 120step=30日では技能形成が起きない → 二相クロックを提案
2. **条件Cの位置づけ**（§19）: Cとの差はH2の証拠にならない → Cを床、Bを主対照に再定義することを提案
3. **Phase 1 の妥当性判定基準**（§8, §29）: 「再現できた」の基準が未定義 → 定性的パターン一致で定義することを提案

**本レビューの姿勢**: SPEC.md は完成度の高い研究仕様である。したがって本文書は「良い点の列挙」ではなく、**研究として成立しない可能性の指摘**に紙幅を割く。指摘の多さは仕様の質の低さを意味しない。

## 1. この研究命題を実装する上での技術的リスク

### 1.1 三すくみ: LLMの非決定性 × 統計的検出力 × APIコスト 【実装提案】

本研究の設計は3つの要求を同時に課しており、これらは互いにトレードオフの関係にある。

- §23 は「LLMの非決定性があるため、単一runだけで結論を出さない設計」を要求する
- §16 は N=30〜50 という小さな母集団を指定する（分散が大きい）
- §19 は3条件の比較を要求する
- §24 はAPIコストの抑制を要求する

必要run数を n とすると、総LLM呼び出し量は `3条件 × n seeds × (agent-steps × 発火率)` に比例する。N=40 と小さいため条件間の差を検出するには n を大きく取る必要があるが、n を大きくすればコストが線形に増える。

**緩和策**:
- Milestone 1 を完全にLLM非依存にする（SPEC §28 の指示通り）。M1 の決定論的部分は無限に再実行でき、統計的性質の把握に費用がかからない。
- **主要な統計的検定は M1 の決定論的世界で行い、LLM は M2 以降の「上乗せ効果」の測定に限定する**。これによりコストのかかる部分の必要run数を減らせる。
- 条件間比較には対応のある設計（同一seedで A/B/C を生成し、seed をブロック要因として扱う）を用いる。これは独立標本より必要nが小さくて済む。

### 1.2 ホストLLMでは厳密な再現性が原理的に確保できない 【実装提案】

SPEC §23 は「同一条件で再実行可能にします」と要求するが、外部APIのモデルは更新・非推奨化されうるため、6ヶ月後に同じ出力を得る保証はない。これは本プロジェクト固有の欠陥ではなく、LLMを使う全ての計算社会科学研究が抱える制約である。

**緩和策**: 「再現性（reproducibility）」を「リプレイ可能性（replayability）」に置き換える。

- モデルIDを完全な文字列で固定・記録する（例: `claude-sonnet-5`）
- **全LLM入出力を `(prompt_hash, model_id, prompt_version)` をキーにキャッシュへ永続化する**
- 再実行時はキャッシュから読む。キャッシュヒットすれば完全に同一の軌跡が再現される
- キャッシュはコスト削減策でもある（§11 で再掲）

この設計では「新規性のある実行」と「検証のためのリプレイ」が明確に分離される。論文に添付すべきはコードとキャッシュの両方になる。

### 1.3 「再構成（reconfiguration）」の表現問題 — 最大の設計リスク 【実装提案】

本研究の核心は「既存の技能・設備が未知の需要へ再構成されるか」である。これをコード上でどう表現するかが、成否を分ける。

3つの選択肢があり、両端は失敗する:

| 方式 | 問題 |
|---|---|
| **名称照合**（`if item.name == "mask": required_skill = "sewing"`） | 答えを埋め込んでいる。SPEC §12・§18 に真っ向から違反 |
| **LLMに自由判断させる** | コード側が実現可能性を判定できない。SPEC §13 に違反 |
| **属性ベクトルの充足判定** | ✅ 採用すべき方式 |

**採用案**: 需要も、技能も、材料も、設備も、すべて**同じ属性空間上のベクトル**として表現する。Agent が「ある材料・技能・設備の組み合わせ」を提案したとき、コード側はその組み合わせが生成する属性ベクトルが要求仕様を充足するかを純粋な数値計算で判定する。名称は一切参照しない。

この設計であれば、Phase 2 で全く新しい要求仕様を注入しても、同じ判定関数が動く。詳細は §6 に記述。

### 1.4 Windows環境固有のリスク 【実装提案】

- **文字コード**: 本セッションで既に `Get-Content SPEC.md` が文字化けする事象を観測している（ファイル自体はUTF-8で正常）。全てのファイルI/Oで `encoding="utf-8"` を明示すること。デフォルトに依存しない。
- **matplotlib**: ヘッドレス実行時に `matplotlib.use("Agg")` を明示。
- **パス**: `pathlib.Path` を使用し、文字列連結によるパス構築を禁止。
- **改行コード**: 既に git が `LF will be replaced by CRLF` を警告している。出力CSV/JSONLの改行コードを固定するため `newline=""` を明示。

## 2. シミュレーションとして成立しない可能性のある箇所

本節が本レビューで最も重要である。

### 2.1 H2 のトートロジー化リスク 【実装提案】

**問題の構造**: Capability Reproduction Loop を機構としてコードに実装すれば、「ループがある世界の方が能力が伸びる」は**構成上自明**になる。これは検証ではなく同語反復である。

論理を明示すると:

```
実装:  loop_enabled == True  →  share が近傍の success_prob を上げる
結果:  loop_enabled == True  →  技能が速く伸びる
```

これは「そう実装したから、そうなった」以上のことを言っていない。査読者はここを最初に突く。

**非自明な主張に落とすための設計**:

H2 を「ループがあると速い（Yes/No）」ではなく、**「どう速いか」の関数形**の問題として立てる。具体的には以下を測定対象にする。

1. **非線形性**: Latent Capability の成長は線形加算か、それとも自己触媒的（成長率が現在の Maker 密度に依存）か。後者であれば「文化は臨界量を超えると質的に変わる」という非自明な主張になる。
2. **閾値効果**: 初期 Maker 比率を掃引したとき、最終 Maker 数に不連続な跳躍点が存在するか。
3. **トポロジー依存性**: エッジ数を固定したまま構造（クラスタ係数、次数分布の歪度、ハブの有無）だけを変えたとき、結果が変わるか。**変わらなければ「文化ネットワーク」という概念は本モデル上では「エッジ数」に還元される**。これは重要な否定的知見であり、報告する価値がある。

**棄却条件の事前明文化（必須）**:

| 仮説 | 棄却される観測 |
|---|---|
| H1 | 条件A において、シミュレーション期間内に Maker 段階への遷移が有意に増加しない |
| H2 | 条件A と条件B の Latent Capability 成長率に、seed をブロックとした検定で有意差がない |
| H3 | 条件間で Latent Capability に差があっても、転化確率・転化速度・供給量に差が伝播しない |

これを実験開始前に固定し、`docs/PREREGISTRATION.md` に記録すべきである。

### 2.2 条件C はほぼトートロジーである 【要承認 → §12-2】

§19 の条件C は「相互学習・ネットワークをほぼ除去」と定義されている。学習チャネルを除去すれば学習が遅いのは、機構上自明である。**したがって A と C の差は H2 の証拠にならない。**

C は「機構が正しく動いていることの床（sanity check）」としては有用だが、主張の根拠にはできない。詳細と変更案は §12-2 に4点セットで記述。

### 2.3 条件B の交絡 — 次数分布を保存しないと結果が汚れる 【実装提案】

条件B は「初期技能・設備分布はAと同一。文化ネットワークをランダム化」と定義される。ここで素朴に「エッジを張り直す」と、次数分布まで変わりうる。すると B が A より遅い理由が「構造が違うから」なのか「単にエッジが減った/ハブが消えたから」なのか判別できない。

**採用案**: **次数保存リワイヤリング（degree-preserving double-edge swap）** を使う。`networkx.double_edge_swap()` が利用可能。これにより:

- 各ノードの次数は完全に保存される
- 総エッジ数も保存される
- 変わるのは「誰と誰が繋がっているか」の構造だけ

さらに厳密を期すなら、条件Bを2段階に分ける:

- **B1（構造ランダム化）**: 次数保存リワイヤリング。技能と接続構造の相関だけを壊す。
- **B2（完全ランダム）**: Erdős–Rényi で同じ平均次数。次数分布も壊す。

B1 との差が本命の知見、B2 は補助。

### 2.4 `community_supply_share` の分母問題 【実装提案】

§20 の転化条件の第一項は `community_supply_share >= threshold` である。この指標の分母には産業側（Manufacturer）の供給が入る。したがって:

> **Manufacturer の生産能力パラメータを下げれば、community_supply_share はいくらでも上げられる。**

主要な結論指標が、単一の恣意的パラメータに支配されている。これは §30 の Anti-Goal「結果が出るように後からパラメータを恣意的調整する」への最短経路である。

**緩和策**:
1. Manufacturer のベース能力を**外部アンカーで固定する**（例: 需要ピーク時に需要のX%を満たせる能力、として X を先に決め打つ）。決定は人間が行う（§12 の未決事項）。
2. **感度分析を必須にする**。`experiments/threshold_sweep.py` で Manufacturer 能力を掃引し、「条件間の順序関係がこの範囲で保たれる」ことを示す。順序が保たれる範囲が狭ければ、それ自体が報告すべき知見である。
3. 分母依存のない補助指標を併記する: `active_supplier_count`（絶対数）、`community_absolute_supply`（絶対量）。

### 2.5 統計的検出力 【実装提案】

N=30〜50、条件3つ、LLMの確率性。この条件で「差がある」と言うには:

- **seed数の下限を事前に決める**（power analysis、または最低でも各条件20〜30 run）
- **効果量と信頼区間を報告する**。p値だけの報告は本設定では意味が薄い
- 対応のある設計（同一seedで A/B/C）により分散を削減する

### 2.6 時間スケール 【要承認 → §12-1】

§25 の「1 step = 6時間、120 steps = 30日」では、Consumer → Maker の技能形成が起きるとは考えにくい。現実の技能習得には数ヶ月〜数年を要する。30日で起こすには学習率を非現実的に高く設定する必要があり、それは §30 の恣意的調整に接近する。詳細は §12-1。

### 2.7 世界の単純さがもたらす限界 【実装提案・注記】

Hospital 1、Manufacturer 1、Logistics 1 という構成は、需要をスカラー1本に潰す。これにより:

- 空間構造がない → 物流の意味が希薄
- マッチング問題がない → 「誰が誰に供給するか」の調整が自明化しうる
- `coordination_edges`（§22）が測る「調整」の内実が薄くなるおそれ

MVPとしては妥当だが、**Emergence Level E3（分業・協調ネットワーク形成）を観測可能にするには、需要側に複数の要求仕様、あるいは工程分割を導入する必要がある**。Milestone 1 では単一需要でよいが、M3 の設計時に「E3 が原理的に発生しうるか」を再確認すること。

## 3. LLMによる既知知識リークのリスク

**本研究の生命線。**

### 3.1 問題の構造

Phase 1（§8）は、現実に起きた「文化的技能 → 医療物資への転用」現象を、個別具体的な行動命令なしに再現できるか検証する。しかし LLM はこの事例を学習済みである。

CLAUDE.md の絶対ルールは、Agentプロンプトに特定の4語を出さないことを要求している。これは必要だが**不十分**である。語を伏せても、以下の要求仕様の組み合わせから LLM はほぼ確実にパターン照合する:

```
可撓性のある材料 + 濾過性能 + 顔面への密着形状 + 高い衛生要求 + 医療機関からの大量需要
```

このとき Agent が示す「創発」は、**推論ではなく記憶の想起**である。Phase 1 の主張は根底から崩れる。

### 3.2 多層防御

#### (a) 禁止語の機械的強制 【実装提案】

CLAUDE.md の絶対ルールを、人間の注意力ではなく**自動テスト**で強制する。

- Agent に渡る全文字列（system prompt、user prompt、Action名、Item名、Material名、ログに残る記述）を収集し、禁止語リストとの照合を行うテストを `tests/test_no_answer_leak.py` として実装
- 禁止語は大文字小文字・日英両方をカバー
- このテストが落ちたら CI を止める

#### (b) 固有名詞の全廃 【実装提案】

材料・技能・要求仕様から名称を排除し、抽象属性ベクトルのみで記述する。「布」「不織布」ではなく `Material(flexibility=0.9, filtration=0.1, ...)`。

ただし完全な無名化は Agent の推論を困難にしすぎる恐れがあるため、**中立的なコードネーム**（`material_A`、`skill_3`）を用いる。実験ログには対応表を残すが、Agent には渡さない。

#### (c) リークプローブ — 定量的な漏洩検査手続き 【実装提案】

完成したプロンプトを、シミュレーションとは無関係な別のLLMインスタンスに提示し、こう問う:

> 「以下は何らかの状況設定です。これは現実のどの出来事を指していますか。分からなければ『不明』と答えてください。」

回答に特定の実事象が現れたら、プロンプトは漏洩している。これを**プロンプトのリリース前チェックとして手続き化**し、結果を記録する。定量的な漏洩指標として論文に載せられる。

#### (d) 最も強力な防御は設計側にある 【実装提案 — 最重要】

主要な従属変数を「転化が起きたか（絶対値）」ではなく、**条件A/B/Cの差分**に置く。

理由: 事前知識は3条件で**共通**である。同じモデル、同じプロンプト、同じ需要仕様を使う限り、「LLMがPPEを知っている」という事実は3条件すべてに等しく効く。したがって**差分を取れば相殺される**。

```
観測されるもの = 真の文化効果 + LLM事前知識バイアス
条件A - 条件B  = (真の文化効果_A - 真の文化効果_B) + (バイアス - バイアス)
              = 真の文化効果の差
```

この論理は本研究の妥当性を支える最も重要な柱であり、**RESULTS.md の冒頭に明記すべきである**。「LLMが知っているから無効だ」という批判に対する正面からの回答になる。

（注: 厳密には、事前知識が条件によって異なる作用をする交互作用の可能性は残る。例えば「ネットワークが密な世界でだけ既知知識が発火しやすい」など。これは限界として明記する。）

#### (e) M1 がLLM非依存であること自体が統制条件 【実装提案】

Milestone 1 は完全に決定論的コードで動く。ここには LLM の事前知識が一切入らない。したがって:

- **M1 の結果 = 純粋に機構が生む効果**
- **M2/M3 の結果 − M1 の結果 = LLM が寄与した分**

この差分が、LLMの寄与（と事前知識の影響）を分離する自然な設計になっている。SPEC §28 の Milestone 構成は、意図されていたか否かに関わらず、リーク対策として非常に良い設計である。

## 4. Capability Reproduction Loop を実装する最小モデル案

### 4.1 設計原則

SPEC §5 の注意書き:

> これは固定された手続きとしてAgentに実行させるものではありません。Agent間相互作用の結果として、この循環がマクロに形成されるよう設計してください。

これを満たすため、**各Agentは局所行動しか持たず、ループはマクロ観測量としてのみ現れる**設計にする。どのAgentも「ループを実行する」コードを持たない。

### 4.2 最小構成要素

ループを閉じるのに必要な要素は、驚くほど少ない。

**(1) 制作と学習**

```
success_prob = f(skill, asset, effective_difficulty)
成功 → 技能獲得 Δs（収穫逓減）+ 新Methodの生成
失敗 → 小さな技能獲得 + 材料損失
```

失敗からも学習させることが重要（現実の制作行動の性質であり、かつ初期段階での完全な停滞を防ぐ）。

**(2) 共有**

```
share(method) → 近傍AgentのinboxへMethodを配送
```

**(3) 足場かけ（scaffolding）— ループを閉じる唯一の環**

```
effective_difficulty = base_difficulty × (1 - scaffolding_effect(known_methods))
```

Method を持っていると、そのプロジェクト種別の**実効難度が下がる** → 成功率が上がる → 技能獲得が加速する → 新たな Method が生まれる → 共有される。

**ここが唯一のループ閉じ目である。これ以上の機構を最小モデルに入れてはいけない。**

```
Aのshare → Bの成功率↑ → Bの成功 → Bのshare → Cの成功率↑ → ...
```

**(4) 段階遷移**

```
maker_stage = g(max_skill, skill_breadth, assets, completed_projects)
```

決定論的関数。閾値は config。

### 4.3 技能減衰を必ず入れる 【実装提案】

減衰がないと技能は単調増加になり、**H1「Maker人口は増加するか」が構成上自明になる**（下がる仕組みがないのだから増えるに決まっている）。

```
練習しなかった技能: s ← s × (1 - decay_rate)
```

減衰があれば、「学習の流入が減衰を上回るか」が非自明な問いになり、H1 が実質的な仮説になる。**これはH1を仮説として成立させるために必須の要素である。**

### 4.4 何を入れないか

最小モデルの規律として、以下は M1 では入れない:

- 金銭経済の詳細（取引はM1では省略可）
- 物流の遅延
- 品質のばらつき
- 市場価格の内生的決定

これらは M3（供給ショック）で必要になったときに追加する。

## 5. Agent state schema の改善案

SPEC §11 のスキーマを基礎に、以下を提案する。変更理由を各項目に付す。

### 5.1 提案スキーマ

```python
from dataclasses import dataclass, field

@dataclass
class Skills:
    """連続値の技能。名称は中立的なコードネームに置換して Agent へ渡す。"""
    sewing: float = 0.0       # 0.0 - 1.0
    crafting: float = 0.0
    cad: float = 0.0
    printing_3d: float = 0.0
    electronics: float = 0.0
    repair: float = 0.0

@dataclass
class Experience:
    """【改善】技能値とは別に、行為の回数を保持する。
    理由: 収穫逓減の計算に必要。また、技能減衰と『経験は残るが腕は鈍る』
    の区別を可能にする。"""
    practice_count: dict[str, int] = field(default_factory=dict)
    success_count: dict[str, int] = field(default_factory=dict)
    failure_count: dict[str, int] = field(default_factory=dict)

@dataclass
class Assets:
    sewing_machine: bool = False
    printer_3d: bool = False
    tools: int = 0            # 0-3 の段階
    workspace: bool = False

@dataclass
class Resources:
    money: float = 0.0
    time_budget: float = 0.0  # 【改善】1step あたりの可処分時間。行動が消費する。
    materials: dict[str, float] = field(default_factory=dict)

@dataclass
class PerceivedSkill:
    """【改善・最重要】他Agentの能力を『真値』ではなく『信念』として持つ。
    理由: SPEC §14 Information Locality を規約ではなく構造で担保するため。
    真値を持たせると、実装者がうっかり神の視点を使ってしまう。"""
    estimate: float
    last_updated_step: int
    confidence: float         # 観測回数から算出

@dataclass
class Method:
    """【改善】共有される『手順知識』を第一級オブジェクトにする。
    理由: source_agent_id と acquired_step を持たせることで、
    knowledge_diffusion_speed が副産物として測定可能になる。
    誰が誰からいつ学んだかの全履歴が、追加コストなしで取れる。"""
    method_id: str
    target_profile: "AttributeVector"   # どんな属性の物を作る手順か
    required_skill_level: float
    difficulty_reduction: float          # scaffolding 効果の大きさ
    source_agent_id: str                 # 【重要】伝播経路の追跡用
    origin_agent_id: str                 # 【重要】最初の発明者
    acquired_step: int
    hop_count: int                       # 【重要】発明者からの伝播ホップ数

@dataclass
class Memory:
    recent_events: list = field(default_factory=list)
    learned_methods: dict[str, Method] = field(default_factory=dict)
    previous_projects: list = field(default_factory=list)
    rejected_intents: list = field(default_factory=list)
    # 【改善】却下された意図の履歴。理由: コード側が実現不可能と判定した
    # 行動を Agent へフィードバックすることで、これ自体が学習信号になる（§8参照）。

@dataclass
class Culture:
    participation_level: float
    maker_stage: str                # Consumer/Customizer/Maker/AdvancedMaker
    sharing_tendency: float
    imitation_tendency: float
    helping_norm: float

@dataclass
class Agent:
    id: str
    role: str
    resources: Resources
    skills: Skills
    experience: Experience          # 【改善】追加
    assets: Assets
    culture: Culture
    memory: Memory

    # 【改善】ネットワーク。真値ではなく信念で保持。
    known_agents: set[str] = field(default_factory=set)
    trust: dict[str, float] = field(default_factory=dict)
    perceived_skills: dict[str, dict[str, PerceivedSkill]] = field(default_factory=dict)

    # 【改善】情報授受をメッセージ経由に限定する。
    # 理由: 神の視点の禁止を「規約」ではなく「構造」で担保する。
    inbox: list = field(default_factory=list)
    outbox: list = field(default_factory=list)

    # 【改善】Agentごとの独立seed stream。
    # 理由: 実行順序が変わっても再現性が壊れない。マスターseedの子として生成。
    rng_seed: int = 0

    current_action: str | None = None
```

### 5.2 主要な改善点と理由

| 改善 | 理由 |
|---|---|
| `known_skills_of_others` → `perceived_skills`（信念化） | §14 を構造で担保。真値を置くと必ず漏れる |
| `inbox`/`outbox` の追加 | 情報授受をメッセージ経由に限定。神の視点を構造的に禁止 |
| `skills` と `experience` の分離 | 収穫逓減と減衰の両方が表現可能に |
| `Method` の第一級オブジェクト化 | `knowledge_diffusion_speed` が副産物として測定可能 |
| Agent ごとの独立 RNG stream | 実行順序の変更に対して再現性が頑健になる |
| `rejected_intents` の追加 | コード側の却下を学習信号として再利用（§8） |
| `free_time` → `time_budget` | 行動が時間を消費する形にし、資源制約を明示化 |

### 5.3 条件間で守るべき不変条件 【実装提案・重要】

§19 は「可能な限り同じseedから初期Agentを生成し、文化構造だけを変えられるように」と要求する。実装上、以下を厳守する。

**条件 A/B/C で同一でなければならないもの**:
- 全 Agent の初期 `skills`、`assets`、`resources`
- 全 Agent の `culture` 特性（`sharing_tendency` 等）の乱数draw
- 需要の発生タイミングと規模
- 各 Agent の RNG stream の初期値

**条件間で変えてよいもの**:
- ネットワークの接続構造のみ
- （条件Cのみ）学習チャネルの有効/無効フラグ

`sharing_tendency` を条件ごとに引き直すと、それだけで結果が変わりうる。**初期化を「Agent生成」と「ネットワーク構築」の2フェーズに厳密に分離し、条件分岐は後者にのみ置く**こと。これはテストで検証する（§10）。

## 7. Event system 案

### 7.1 1ステップの構造

```
for each step:
    1. perceive   : 各Agentの Observation を構築（局所情報のみ）
    2. decide     : 各Agentが Intent を返す（M1: ルール、M2以降: LLM）
    3. act        : Intent を収集（この時点では世界を変えない）
    4. resolve    : 全Intentを一括解決（同時解決）
    5. update     : 資源・技能・ネットワーク・段階を更新
    6. record     : Metrics を記録
```

**同時解決（4）が重要**: 逐次解決だと「早い者勝ち」で行動順序が結果に影響する。全 Intent を収集してから一括解決することで、順序の有利不利を排除する。資源が競合する場合の解決順序は、マスターRNG由来のシャッフルで決める（seed固定なので再現可能）。

### 7.2 イベント型

```python
class EventType(Enum):
    MESSAGE_RECEIVED   = "message_received"     # 他Agentからの情報到着
    METHOD_SHARED      = "method_shared"        # Methodの共有が発生
    MAKE_SUCCEEDED     = "make_succeeded"
    MAKE_FAILED        = "make_failed"          # 失敗
    PROPOSAL_RECEIVED  = "proposal_received"    # 協力提案の受信
    DEMAND_ANNOUNCED   = "demand_announced"     # 新需要の観測
    STAGE_CHANGED      = "stage_changed"        # maker_stage の遷移
    SHOCK_STARTED      = "shock_started"
    INTENT_REJECTED    = "intent_rejected"      # コード側が実現不可能と判定
```

### 7.3 設計上の要点: Event system がそのままコスト制御機構になる 【実装提案】

SPEC §24 の「LLM呼び出し候補」リストと、上記イベント型が**ほぼ1:1で対応している**。

| §24 の呼び出し候補 | 対応するイベント |
|---|---|
| 新情報を受け取った | `MESSAGE_RECEIVED` / `METHOD_SHARED` |
| 新需要を知った | `DEMAND_ANNOUNCED` |
| 制作に失敗した | `MAKE_FAILED` |
| 他Agentから提案された | `PROPOSAL_RECEIVED` |
| 新しい用途を検討する | `SHOCK_STARTED` |
| 協力相手を選ぶ | `PROPOSAL_RECEIVED` |

したがって**イベントシステムを作れば、コスト制御機構が同時に手に入る**。「イベントが発火した Agent のみ LLM を呼ぶ」という単一のルールで、§24 の要求が満たされる。この統合を設計の軸とすることを提案する。

## 8. LLM / deterministic code の責務分離案

### 8.1 責務表（SPEC §13 の整理）

| 領域 | 担当 | 補足 |
|---|---|---|
| 局所的な意思決定（次に何をするか） | **LLM** | M1では決定論的ルールが代行 |
| 情報の解釈 | **LLM** | |
| 他Agentとのコミュニケーション内容 | **LLM** | |
| 新しい用途の提案（レシピの構成） | **LLM** | 本研究の核心部分 |
| 協力するか否かの判断 | **LLM** | |
| 学習対象の選択 | **LLM** | |
| 資源・在庫・所持金・時間の計算 | **Code** | |
| 生産量・材料消費 | **Code** | |
| 技能値の更新 | **Code** | |
| 設備制約の判定 | **Code** | |
| 属性充足判定・品質判定 | **Code** | §6 の `satisfies()` |
| 市場・物流 | **Code** | |
| ネットワーク更新 | **Code** | |
| Metrics・転化判定 | **Code** | |

### 8.2 境界の実装形式 【実装提案】

原則「LLM decides intent. Code determines feasibility.」を、**型で強制する**。

```python
@dataclass(frozen=True)
class Intent:
    """LLM が返せる唯一の型。数量を含めない。
    【重要】production_quantity, money_amount 等のフィールドを
    意図的に持たせない。LLMが『一晩で1万個作れる』と言えない構造にする。"""
    action: ActionType                  # enum。make_ppe 等は存在しない
    target_agent_id: str | None
    recipe_sketch: RecipeSketch | None  # 材料・技能の組み合わせ案（量ではない）
    reason: str                         # 短い理由（ログ・分析用）
```

処理フロー:

```
LLM → Intent（構造化出力）
  ↓
Validator（コード）: 時間・材料・所持金・技能・設備の充足を判定
  ↓
  ├─ 実現可能 → Executor が実行。数量はコードが計算
  └─ 実現不可 → RejectedIntent(reason) を Agent の memory へ返す
                 → これ自体が次ステップの学習信号になる
```

**却下を学習信号にする**点が重要である。「材料が足りずに作れなかった」という経験が memory に残り、次の意思決定の入力になる。これは現実の制作行動に対応しており、かつ余計な機構を追加せずに実現できる。

### 8.3 構造的に禁止すること

- LLM の出力スキーマに数量フィールドを置かない（上記）
- LLM に他Agentの真の技能値を見せない（`PerceivedSkill` のみ）
- LLM に市場全体の集計値を見せない（観測可能な範囲のみ）
- Action enum に答えを含む値を定義しない（テストで強制、§10）

## 9. Milestone 1 の具体的実装計画（方針）

詳細設計は `docs/DESIGN_M1.md` に分離した。ここでは方針と、最も重要な注意点のみ記す。

### 9.1 構築順序

```
1. config ローダ + 再現性メタデータ記録（seed, timestamp, config hash）
2. AttributeVector / Material / Recipe / RequiredItem
3. Agent データ構造 + 初期化（seed から決定論的に生成）
4. ネットワーク構築（A / B1 / B2 / C の4条件）
5. Observation 構築（局所情報のみを切り出す）
6. 決定論的意思決定ルール（効用ベース）
7. アクション: observe / ask / practice / make / share
8. 技能獲得・減衰・maker_stage 遷移
9. Metrics 記録 + CSV/JSONL 出力
10. テスト一式（§10）
```

### 9.2 M1 の成功条件 — ここを間違えてはいけない 【実装提案・最重要】

**やってはいけない定義**:

> ❌ 「条件A が条件C より Maker 数が多くなること」

これを M1 の成功条件にすると、そうなるまでパラメータを触ることになる。それは §30 の Anti-Goal「結果が出るように後からパラメータを恣意的調整する」そのものである。

**正しい定義**:

> ✅ **機構が動作し、Metrics が測定可能であること**

具体的には:

1. 4条件すべてが例外なく完走する
2. 同一seedで2回実行して状態ハッシュが一致する（決定論性）
3. 資源保存則が破れない
4. `Consumer → Customizer → Maker` の遷移が**少なくとも発火しうる**ことを、固定シナリオのテストで確認する
5. §22 の全 Metrics が算出され、出力される
6. 禁止語テストが通る

**条件間の差の有無は、M4 における「観測結果」であって、M1 の合格条件ではない。** この区別を DESIGN_M1.md の完了判定にも明記する。

### 9.3 パラメータの扱い

M1 のパラメータ（学習率、減衰率、成功確率の形状、段階遷移閾値）は**仮置き**であり、以下の規律で扱う:

- config YAML に全て外出しする。コードに数値を埋め込まない
- 「もっともらしい値」を初期値として置き、**結果を見て調整しない**
- 感度分析（`experiments/threshold_sweep.py`）で、結論がパラメータ範囲にどう依存するかを示す
- 実験開始前に値を固定し、事前登録する（§20 の「最終値は実験開始前に固定します」に対応）

    obs = build_observation(world, agent)

    for other in obs.perceived_skills.values():

## 11. 想定APIコストを抑える設計案

### 11.1 Milestone 1 はコストゼロ

M1 は LLM を使わない。したがって M1 の開発・デバッグ・パラメータ探索・感度分析はすべて無料で行える。**最も試行錯誤が多い段階にコストがかからない**設計になっている。

### 11.2 ハード上限とアボート機構（CLAUDE.md 絶対ルールで必須）

```python
class CostGuard:
    """累積コストを監視し、上限超過で実行を停止する。
    CLAUDE.md 絶対ルール『API費用の上限を設定し、超えたら実行を止める』の実装。"""
    def __init__(self, max_usd: float, checkpoint_dir: Path):
        self.max_usd = max_usd
        self.spent_usd = 0.0

    def record(self, model: str, input_tokens: int, output_tokens: int) -> None:
        self.spent_usd += price_of(model, input_tokens, output_tokens)
        if self.spent_usd >= self.max_usd:
            self.save_checkpoint()
            raise BudgetExceeded(
                f"予算上限 ${self.max_usd} に到達（実績 ${self.spent_usd:.2f}）。"
                f"チェックポイントを保存して停止しました。"
            )
```

- 上限値は config で指定し、**実行開始時にログへ明記する**
- 超過時はチェックポイントを保存してから停止する（作業を失わない）
- 警告閾値（例: 80%）で警告を出す

### 11.3 二重キャップ

| キャップ | 目的 |
|---|---|
| 1 Agent 1 step あたりの呼び出し上限（例: 1回） | 単一Agentの暴走を防ぐ |
| 1 run あたりの総呼び出し上限 | run全体の上限 |
| 累積コスト上限（上記 CostGuard） | 最終防衛線 |

### 11.4 レスポンスキャッシュ — 一石二鳥

`(prompt_hash, model_id, prompt_version)` をキーにレスポンスを永続化する。

- **コスト削減**: 同じ状況が再現したとき、API を呼ばない
- **再現性**: リプレイ時にキャッシュから読めば、完全に同一の軌跡が再現される（§1.2）

この2つが単一の機構で同時に達成される。

### 11.5 モデルのティア分け

SPEC §24 の「通常状態→Code、軽い意思決定→cheap model/rule、重要な再構成判断→capable LLM」を、具体的なモデル選定に落とす。

| 用途 | 推奨モデル | 入力 / 出力（$/1Mトークン） |
|---|---|---|
| 通常状態 | LLM を使わない（ルール） | $0 |
| 軽い意思決定（学習対象の選択など） | `claude-haiku-4-5` | $1.00 / $5.00 |
| 標準的な局所判断 | `claude-sonnet-5` | $3.00 / $15.00（2026-08-31まで導入価格 $2.00 / $10.00） |
| 重要な再構成判断（ショック時の用途転換） | `claude-opus-5` | $5.00 / $25.00 |

（価格は 2026-08-15 時点。本日時点で Sonnet 5 は導入価格が適用される。）

### 11.6 コスト試算の式

具体的な予算はユーザーが決める（§12）が、見積もりの式を示す。

```
総呼び出し数 = N_agents × steps × 発火率 × 条件数 × seed数
総コスト     = 総呼び出し数 × (in_tokens × 入力単価 + out_tokens × 出力単価)
```

**試算例**（M2 の初期実験を想定）:

| 変数 | 値 |
|---|---|
| N_agents | 40 |
| steps | 120 |
| 発火率（event-driven） | 10% |
| 条件数 | 4（A/B1/B2/C） |
| seed数 | 5（初期テスト） |
| 1呼び出しの入力トークン | 800（構造化・簡潔なプロンプト） |
| 1呼び出しの出力トークン | 150（構造化出力） |

```
総呼び出し数 = 40 × 120 × 0.10 × 4 × 5 = 9,600 回
入力トークン = 9,600 × 800   = 7.68M
出力トークン = 9,600 × 150   = 1.44M
```

- **Haiku 4.5 の場合**: 7.68 × $1.00 + 1.44 × $5.00 = **約 $14.9**
- **Sonnet 5 の場合（導入価格）**: 7.68 × $2.00 + 1.44 × $10.00 = **約 $29.7**
- **Sonnet 5 の場合（通常価格）**: 7.68 × $3.00 + 1.44 × $15.00 = **約 $44.6**
- **Opus 5 の場合**: 7.68 × $5.00 + 1.44 × $25.00 = **約 $74.4**

本実験（seed 20〜30）ではこの4〜6倍になる。プロンプトキャッシュを併用すれば入力側は大幅に下がる。

**重要**: 上記は概算であり、実際の消費はプロンプト長に強く依存する。**M2 の最初の1 run で実測し、そこから外挿すること。** 見積もりで予算を決めない。

### 11.7 その他の削減策

- **構造化出力**を使い、出力トークンを最小化する（自由記述の散文を返させない）
- **プロンプトキャッシュ**: 世界の共通説明部分を先頭に置き、Agent固有情報を後ろに置く（前方一致でキャッシュが効く）
- Observation を簡潔にする。Agent に渡す情報が多いほど入力トークンが増える
- 全 LLM 呼び出しの `call数 / input_tokens / output_tokens / 推定費用` をログする（§24 の要求）

#### 【要承認 1】時間スケール（§25）

**問題**
SPEC §25 は「1 step = 6時間、4 steps = 1日、120 steps = 30日」と定めている。一方 §28 の Milestone 1 は「`Consumer → Customizer → Maker` の遷移を確認する」ことを目標としている。この2つは両立しない可能性が高い。

**なぜ問題なのか**
現実のコスプレ制作技能（縫製・造形・CAD・3Dプリント）の習得には、数ヶ月から数年を要する。30日で Consumer から Maker への遷移を起こすには、学習率を非現実的に高く設定しなければならない。これは2つの帰結を生む。

1. H1「相互学習構造は時間経過とともに Maker 人口を増加させるか」が、30日という窓では測定不能になる
2. 無理に起こそうとすると、パラメータを結果に合わせて調整することになり、§30 の Anti-Goal に抵触する

さらに、H2 が問う「Latent Capability の成長速度差」も、蓄積期間がなければ差が現れる余地がない。文化的蓄積は本来「平時に長期間かけて起こる」というのが §31 の中心命題そのものである。

**変更案**
**二相クロック**の導入を提案する。

| 相 | 期間 | 時間解像度 | 目的 |
|---|---|---|---|
| **蓄積相（Accumulation Phase）** | 1〜3年相当 | 1 step = 1週間 | 文化活動による技能・設備・関係性の形成。H1・H2 の測定対象 |
| **ショック相（Shock Phase）** | 30日 | 1 step = 6時間 | 供給ショックへの応答。H3 の測定対象 |

蓄積相は粗い解像度で高速に回せる（LLM呼び出しも少なくて済む）。ショック相のみ §25 の細かい解像度を使う。両相の step 数・解像度は config で変更可能にする。

**変更しなかった場合の影響**
- H1・H2 が測定不能になるか、非現実的な学習率によって人工的に生成された結果になる
- 「平時の文化蓄積が危機時の能力になる」という §31 の中心命題が、モデル上で表現できない
- Phase 1 の妥当性を主張する根拠が弱くなる

> #### ✅ 【決着】承認（2026-08-15）— SPEC §25 / §33 改訂2
>
> 提案どおり **二相クロック**を採用。
>
> - 蓄積相: 1 step = 1週、標準 **156 step**（3年相当）。**52 / 104 / 156 を config 切替**（決定 D11）
> - ショック相: 1 step = 6時間（v0.1 の解像度をそのまま保持）
>
> 旧定義は SPEC §33 改訂2 に原文保存されている。

#### 【要承認 2】条件Cの位置づけ（§19）

**問題**
§19 の条件C は「初期技能・設備分布はAと同一。相互学習・ネットワークをほぼ除去」と定義される。しかし学習チャネルを除去すれば学習が遅くなるのは、機構上自明である。

**なぜ問題なのか**
A と C の差は「相互学習を実装したから相互学習の効果が出た」という同語反復にすぎず、H2 の証拠にならない。査読者・審査員はここを最初に指摘する。「文化ネットワークがあると能力が伸びる」という主張の根拠が A−C の差だけであれば、主張全体が棄却されうる。

**変更案**
条件の位置づけを以下のように再定義することを提案する（**条件の構成そのものは変更しない**）。

| 条件 | 位置づけ | 用途 |
|---|---|---|
| **A. Culture** | 処理群 | 主対象 |
| **B. Skill-Matched Random** | **主対照群** | **H2 の本命の検証**。エッジ数・次数分布は同一で、構造のみランダム化 |
| **C. Isolated** | 床（sanity check） | 機構が正しく動いていることの確認。主張の根拠には使わない |

加えて B を B1（次数保存リワイヤリング）と B2（完全ランダム）に分割する【実装提案・§2.3】。

**変更しなかった場合の影響**
- H2 の「検証」が同語反復として棄却される
- 「同じ技能・設備を持つ集団でも文化構造の有無で差が出る」という §29 の Phase 1 成功条件が、証明できなくなる
- 最も重要な知見（構造そのものが効くのか、単に接続数が効くのか）が得られない

> #### ✅ 【決着】提案とは異なる形で承認（2026-08-15）— SPEC §19 / §33 改訂1
>
> **本レビューの提案は採用されなかった。より強い形の再設計に置き換えられた。** 経緯を以下に記録する。
>
> **本レビューが提案していたこと:**
> 条件の**構成そのものは変更せず**、位置づけだけを再定義する。すなわち
> 「**C を床（sanity check）に格下げし、B を主対照群に昇格させる**」。加えて B を B1（次数保存リワイヤリング）と B2（Erdős–Rényi）に分割する。
>
> **最終的な決着:**
> 位置づけの変更ではなく、**条件構成そのものを 2×2完全要因計画へ再設計**した。
>
> | 条件 | Topology | Peer learning |
> |---|---|---|
> | **A** | structured | ON |
> | **B** | rewired | ON |
> | **C** | **structured** | **OFF** |
> | **D** | rewired | OFF |
>
> **C は「床」ではなくなった。** C は A と**完全に同一のネットワーク構造**（同一 Graph object の deep copy）を持ち、`peer_learning_enabled` フラグだけが異なる、2×2 の正規の一セルとして再定義された。
>
> **なぜ提案より強いのか:**
>
> 1. **提案では交互作用が推定できない。** 「C を床に格下げして B を主対照にする」のは、依然として topology と peer learning を混合した1因子デザインである。2×2 にして初めて、topology の主効果・peer learning の主効果・両者の交互作用を分離して推定できる。
> 2. **トートロジー問題がより根本的に解消される。** 提案は「A−C の差を主張の根拠に使わない」という**運用上の約束**でトートロジーを回避しようとしていた。最終案は、C から社会的接触を除去せず（`nx.empty_graph()` を使わない）、遮断対象を **peer Method transfer の1経路のみ**に限定することで、**設計そのものからトートロジー性を除去**している。A−C は「つながりの有無」の差ではなく「つながりが能力再生産経路として機能するかどうか」の差になった。
> 3. **B2（Erdős–Rényi）は M1 から削除された。** 次数分布を壊す条件は、次数保存条件（現 B）と役割が重複し、セル数だけを増やす。将来の model specification sensitivity としてのみ再検討する。
>
> **廃止された名称**（§33 に記載。実装に使ってはならない）:
> `A. Culture` / `culture` / `B. Skill-Matched Random` / `B1` / `B2` / `C. Isolated` / `isolated` / Erdős–Rényi条件
>
> **本レビュー §2.2・§2.3・§5.3・§9・§10 に残る旧条件名は、すべて上記に読み替えること。**
> 特に §2.3 の「次数保存リワイヤリングを使う」という指摘（I5）は現行設計にも**そのまま生きている** — 現 B/D の rewired graph がそれである。

#### 【要承認 3】Phase 1 の妥当性判定基準（§8, §29）

**問題**
§8 は「現実に起きた転化現象を、個別具体的な行動命令なしに再現可能か検証する」とし、§9 は「Phase 1でモデル妥当性を確認した後」に Phase 2 へ進むとしている。しかし**「再現できた」と判定する基準が SPEC に存在しない。**

**なぜ問題なのか**
判定基準がないと、「妥当性を確認した」という主張が反証不能になる。反証不能な主張は科学的主張ではない。また、Phase 2 へ進む根拠が「なんとなくそれらしく見えたから」になってしまう。

現実データとの数値一致を基準にすることも困難である。COVID期のメイカー活動について、本モデルのパラメータに対応する定量データは存在しないか、極めて限定的である。

**変更案**
妥当性を**定性的パターン一致**として定義することを提案する。以下3点すべてを満たしたとき「Phase 1 妥当性確認済み」とする。

1. **条件間の順序関係**: 転化指標において A > B > C の順序が、事前登録した seed 数で安定して観測される
2. **Emergence Level の到達**: 条件A において E2（模倣・情報共有の発生）以上が観測される。E3（分業・協調ネットワーク形成）が観測されればより強い
3. **Reconfiguration Time の分布形**: 条件A の再構成時間が有限の分布を持ち、条件C より有意に短い

**明示的に基準としないもの**: 供給量の絶対値、現実データとの数値一致。これらはモデルの自由パラメータに依存しすぎるため。

**変更しなかった場合の影響**
- 「妥当性確認済み」が反証不能な主張になる
- Phase 2 へ進む判断根拠が作れない
- 最終提出物（RESULTS.md）で Phase 1 の結論を書けない

> #### ✅ 【決着】一部修正のうえ承認（2026-08-15）— SPEC §8 / §29 / §33 改訂4
>
> 「妥当性を操作的に定義する」という方針は承認された。ただし**基準の中身は本レビューの提案から変更された。**
>
> **承認された基準（SPEC §8 本文に反映済み）:**
>
> > 局所情報・資源制約・一般化された行動のみから、既存技能・設備の別用途への再構成という現象が**原理的に発生可能であること**
>
> **本レビューの提案から削除された項目:**
>
> | 提案項目 | 扱い |
> |---|---|
> | 1. 条件間の順序関係（A > B > C）が安定して観測される | **削除** |
> | 2. 条件A で Emergence Level E2 以上が観測される | 基準には含めない（E0〜E4 の操作的定義自体が未確定。§12.3 および `docs/DESIGN_M1.md` §18 R2） |
> | 3. Reconfiguration Time が条件C より有意に短い | **削除**（順序関係と同じ理由） |
>
> **削除の理由:**
> 順序関係を妥当性の条件にすると、**その順序が出るまでモデルを調整することが正当化されてしまう**。これは §30 Anti-Goal「結果が出るように後からパラメータを恣意的調整する」に直結する。妥当性判定と仮説検証は分離しなければならない。
>
> - **妥当性** = 機構が原理的に成立しうるか（Phase 2 へ進む条件）
> - **H1/H2/H3** = 観測して報告するもの（Phase 2 へ進む条件では**ない**）
>
> SPEC §19 が「**A < B も正当な研究結果**」と明記している以上、順序関係を妥当性基準に置くことは自己矛盾でもあった。
>
> **供給量の絶対値・現実データとの数値一致を基準にしない**点は、提案どおり維持された。

### 16.2 X3 の決着 — participant / non-participant の因果設計

**当初の懸念**: 30/10 に差を付ける設計は、SPEC §6 が禁じる「コスプレイヤーは技能が高い／利他的である」という未証明の前提を、初期分布として密輸入しかねない。

**決着**: 差を付ける対象を極限まで絞った。

- **差を付けないもの**: `skills` / `assets` / `materials` / `sharing_tendency` / `imitation_tendency` / `helping_norm` / `time_budget` — **すべて共通分布から生成**
- **差を付けるもの**: `participation_level` と cultural peer-learning network への参加資格の**2点のみ**

さらに **non-participant を孤立ノードにしない**ことを必須要件とした。孤立させると、participant との差が「participation の差」と「ネットワーク孤立の差」の**二重差**になり、文化参加効果と単純な社会接触効果が交絡する。これは条件C/Dを `nx.empty_graph()` にしてはならない理由（§12.1【要承認2】の決着）とまったく同じ構造の誤りである。

一般社会接触（`known_agents`）と cultural peer-learning edge（`cultural_peers`）を概念上分離し、後者のみが Method を運ぶ。

**位置づけ**: participant / non-participant は **M1 の主要な因果対照ではない**。主要対照はあくまで A/B/C/D（topology × peer learning）の2×2完全要因計画である。non-participant は **context population** として扱い、**この比較から「文化参加の因果効果」を直接主張しない**。30/10 という比率も現実の人口比を表す実証値ではなく、M1 の仮置き構成である。

Metrics は `all_agents` / `participants_only` / `nonparticipants_only` の3系列で保存し、**H1/H2 の主要判定は `participants_only`** で行う。

### 16.4 trust の最終仕様

**M1 では trust を固定値とし、更新式を実装しない。**

本レビュー §5.1（I12）および SPEC §19 旧記述にあった「`ask` によって `perceived_skills` と `trust` を更新する」は**廃止**した。正しくは「**`ask` によって `perceived_skills` は更新するが、trust は M1 では固定**」である。

**理由**: peer learning の ON/OFF が trust dynamics まで変化させると、操作した因子が2つになり、A−C の差を peer reproduction 経路だけに帰属できなくなる。§12.1【要承認2】の決着が要求した「遮断するのは単一経路のみ」という設計が崩れる。

## 17. maker_stage 判定規則の修正（2026-08-15 第2次査読）

第2次査読で、S1〜S4 を止める矛盾がさらに2件見つかった。うち **Z1 は本レビューの前提そのものに関わる**ため記録する。

### 17.1 Z1 — 判定規則が SPEC §4 の定義から乖離していた

**発見の経緯**: `agent_init` の既定分布（beta(1.5, 8.0) 前後）では、6技能の**最大値**が `customizer_skill = 0.20` を超える確率が約85%となり、初期 Consumer 比率が約15%にしかならない。§15.1 要件1（Consumer ≥ 90%）と正反対の値である。

**当初の見立ては誤りだった。** これは分布パラメータの校正で直すべき問題に見えたが、**問題の本質は判定規則の側にあった**。

SPEC §4 は各段階を**行動の記述**として定義している。

> - **Consumer**: 完成品購入中心。
> - **Customizer**: 既製品の調整・加工、一部制作等を行う。

これは潜在技能の水準ではない。旧規則 `max_skill >= customizer_skill or n_projects >= 1` は、**一度も手を動かしていない高技能者を Customizer と判定していた**。SPEC §4 の定義に照らせば、その人は Consumer である。

**決定**: `max_skill >= customizer_skill` の経路を削除し、Customizer を `n_projects >= 1` のみで判定する。`customizer_skill` は config から削除。

### 17.2 この修正がもたらす副次的な効果 — 校正作業の消滅

初期状態では全Agentが `n_projects = 0` であるため、**Consumer 比率は構成上100%になる**。

これにより §14.1.1 の校正手続きは、技能・設備の初期分布に対しては**適用対象そのものが消滅する**。「Consumer 比率が目標に届かないので技能分布を下げる」という操作が不要になるだけでなく、**構造的に実行できなくなる**。

本レビュー §12.1【要承認3】の決着で確認した「妥当性判定と仮説検証を分離し、結果に合わせた調整を構造的に排除する」という方針が、初期化分布のレベルでも達成された。校正が残るのは `participation_level` の分散と低participation層の存在（要件2・3）のみである。

### 17.3 H1 が自明化しないことの確認

Customizer が不可逆（`completed_projects` は減らない）になるため、「段階が単調増加してしまい H1 が自明になるのではないか」という懸念が生じる。**これは MAKER 以上の判定によって回避されている。**

| 段階 | 判定基準 | 可逆性 |
|---|---|---|
| Customizer | 行動したことがあるか（`n_projects >= 1`） | 不可逆 |
| Maker / Advanced Maker | 現在その能力があるか（`max_skill` + 履歴） | **可逆** |

`maker_count` は `max_skill >= maker_skill` を要求し、`max_skill` は技能減衰（決定 D6）の対象である。したがって **Maker から Customizer へ落ちうる**。H1「相互学習構造は Maker 人口を増加させるか」は「学習の流入が減衰を上回るか」という非自明な問いのまま保たれる（§4.3 の減衰導入意図がそのまま生きている）。
